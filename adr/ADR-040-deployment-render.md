# ADR-040 — Deployment Strategy for Render

| Field | Content |
|-------|---------|
| **Status** | Proposed |
| **Date** | 2026-09-10 |
| **Decision** | Deploy the STMIET Accounting System on **Render** using a managed PostgreSQL add‑on and optional managed Redis. The Django app runs in a single web container (modular monolith, ADR‑009/010). Migrations and `collectstatic` are performed at container start via Render’s start command. |
| **Context** | • Python/Django 5 modular monolith (ADR‑009/010)<br>• PostgreSQL + Redis/Celery<br>• Server‑rendered UI (HTMX + Tailwind) per ADR‑036<br>• No existing CI/CD; Docker‑compose is the local development model<br>• 40 ADRs govern architecture (immutable journal ADR‑005, approval gates ADR‑008/020, tax feed ADR‑033, etc.)<br>• Current scale: 3‑6 concurrent users; priority is fast launch and iteration<br>• Goal: zero‑touch GitHub‑driven deploys, managed DB/Redis, easy migration path to K8s later |
| **Decision Drivers** | 1. **Speed** – Connect GitHub, Render builds the Docker image and deploys on push. No VM ops.<br>2. **Managed PostgreSQL** – Render adds a PostgreSQL instance; `DATABASE_URL` is injected, no manual connection strings.<br>3. **Managed Redis (optional)** – Render Redis add‑on injects `REDIS_URL` for Celery broker/cache.<br>4. **Single‑container model** – Matches ADR‑009/010; no need to split services in the platform layer.<br>5. **Start‑command migrations** – Render lets us specify a command that runs `manage.py migrate --run-sync && manage.py collectstatic --noinput && gunicorn …` before the app serves traffic, guaranteeing DB schema is up‑to‑date on every deploy.<br>6. **Future‑proof** – The same Docker image can be exported and run on any K8s cluster or self‑hosted environment; only the deployment manifest changes.<br>7. **Cost** – Free tier suffices for 3‑6 users; paid “Starter” plan (~$7/mo) adds custom domain + lets‑encrypt TLS. |
| **Consequences** | **Positive**<br>• Push‑to‑deploy from GitHub (main = production, staging branch = UAT).<br>• No server maintenance (OS patches, backups handled by Render).<br>• Managed DB/Redis with built‑in backups, TLS, health‑checks.<br>• Migrations run automatically; zero‑downtime deploys because Render restarts the container after code change.<br>• Simple rollback via Render’s history UI.<br>• Familiar Docker artefacts (`Dockerfile`, `requirements/*.txt`, `manage.py`) remain unchanged.<br><br>**Trade‑offs**<br>• Horizontal scaling limited to Render’s “Starter”/“Pro” plans (add more web instances) – sufficient for 3‑6 users now, can be upgraded later.<br>• No fine‑grained network policies or site‑to‑site VPN; if required, a future move to self‑hosted K8s or a VM is possible.<br>• Render‑specific env‑var naming (e.g., `POSTGRES_DB`, `POSTGRES_USER`) is injected; the app already reads `DATABASE_URL`, so no code change needed. |
| **Co‑related ADRs** | ADR‑009 (modular monolith) → single web container.<br>ADR‑010 (framework decision) → Python/Django 5, gunicorn, WSGI.<br>ADR‑036 (UI frontend) → HTMX/Tailwind assets built during image build.<br>ADR‑005 (immutable journal) → migrations must run before any POSTED JEs; start‑command guarantees this.<br>ADR‑033 (tax feed) → env‑vars for any third‑party credentials stored as Render secrets.<br>ADR‑035 (financial statements) → `collectstatic` must run before FS generation; included in start‑command. |
| **Implementation Outline** | 1. **Add a `render.yaml` (or use the Dashboard) that defines**:<br>   - A web service built from `backend/Dockerfile`.<br>   - A managed PostgreSQL add‑on (version 15).<br>   - (Optional) a managed Redis add‑on.<br>   - A start command: `python manage.py migrate --run-sync && python manage.py collectstatic --noinput && gunicorn config.wsgi:application --bind 0.0.0.0:8000`.<br>   - Environment variables: `SECRET_KEY`, `DJANGO_SETTINGS_MODULE` (set explicitly) – Render injects `DATABASE_URL` and `REDIS_URL` automatically.<br>2. **Connect the GitHub repo** to Render; set the default branch to `main` for production and a `staging` branch for UAT/integration testing.<br>3. **Add secrets** in the Render dashboard for any third‑party keys (e.g., S3, external tax services) referenced by the code via `os.getenv()`.<br>4. **Deploy** – First deploy runs migrations and collects static files; subsequent pushes incrementally apply new migrations.<br>5. **Monitor** – Render’s logs and health checks confirm the app is up; Celery worker can be a separate “background worker” service if needed.<br>6. **Future migration** – When scaling beyond Render’s limits, export the Docker image and create K8s manifests (Deployment, Service, ConfigMap, Secret) – the app code does not change. |
| **Status** | Proposed – awaiting team sign‑off. |

*This ADR replaces any ad‑hoc deployment notes and becomes the single source of truth for how the STMIET Accounting System is released to production on Render.*
