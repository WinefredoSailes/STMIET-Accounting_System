# ADR-040 — Deployment Strategy for Render

| Field | Content |
|-------|---------|
| **Status** | Accepted |
| **Date** | 2026-09-10 |
| **Decision** | Deploy the STMIET Accounting System on **Render** using a managed PostgreSQL add‑on (PG 18). The Django app runs in a single web container (modular monolith, ADR‑009/010), built from the existing `backend/Dockerfile`. Migrations and `collectstatic` are performed at container start via Render's `dockerCommand`. Celery/Redis is **deferred** until it is actually implemented in code. |
| **Context** | • Python/Django 5 modular monolith (ADR‑009/010)<br>• PostgreSQL + Redis/Celery (Redis deferred — no broker config or tasks exist in code yet)<br>• Server‑rendered UI (HTMX + Tailwind) per ADR‑036<br>• No existing CI/CD; Docker‑compose is the local development model (`backend/docker-compose.yml` for dev parity, unused on Render)<br>• 40 ADRs govern architecture (immutable journal ADR‑005, approval gates ADR‑008/020, tax feed ADR‑033, etc.)<br>• Current scale: 3‑6 concurrent users; priority is fast launch and iteration<br>• Goal: zero‑touch GitHub‑driven deploys, managed DB, easy migration path to K8s later |
| **Decision Drivers** | 1. **Speed** – Connect GitHub, Render builds the Docker image and deploys on push via Blueprint (`render.yaml`). No VM ops.<br>2. **Managed PostgreSQL 18** – Render provisions a Postgres instance under the top‑level `databases:` list; `DATABASE_URL` is injected via `fromDatabase`, no manual connection strings.<br>3. **Single‑container model** – Matches ADR‑009/010; no need to split services in the platform layer.<br>4. **Migration‑at‑start** – Render's `dockerCommand` runs `manage.py migrate --run-sync && manage.py collectstatic --noinput && gunicorn …` before the app serves traffic, guaranteeing DB schema and static assets are current on every deploy.<br>5. **Docker build context correctness** – `rootDir: backend` ensures the build context matches the Dockerfile's `COPY requirements/prod.txt` and `COPY . .` (the Dockerfile and all app code live under `backend/`).<br>6. **Hosts allowlist** – `ALLOWED_HOSTS=.onrender.com` is set as an env var; `base.py` defaults it to `[]`, which would cause `DisallowedHost` on every request.<br>7. **Static files** – `STATIC_URL` is absolute (`/static/`) so whitenoise-served assets resolve on nested URLs; `collectstatic` runs in `dockerCommand`.<br>8. **Future‑proof** – The same Docker image can be exported and run on any K8s cluster or self‑hosted environment; only the deployment manifest changes.<br>9. **Cost** – Free tier suffices for 3‑6 users; paid "Starter" plan (~$7/mo) adds custom domain + Let's Encrypt TLS. |
| **Consequences** | **Positive**<br>• Push‑to‑deploy from GitHub (main = production, staging branch = UAT).<br>• No server maintenance (OS patches, backups handled by Render).<br>• Managed DB with built‑in backups, TLS, health‑checks, private networking.<br>• Migrations run automatically at container start; zero‑downtime deploys because Render restarts the container after code change.<br>• Simple rollback via Render's history UI.<br>• Familiar Docker artefacts (`Dockerfile`, `requirements/*.txt`, `manage.py`) remain unchanged.<br><br>**Trade‑offs**<br>• Horizontal scaling limited to Render plans (add more web instances) – sufficient for 3‑6 users now, can be upgraded later.<br>• No fine‑grained network policies or site‑to‑site VPN; if required, a future move to self‑hosted K8s or a VM is possible.<br>• When Celery is implemented, a Key Value (Redis) service must be added to `render.yaml` and `REDIS_URL` wired via `fromService`. |
| **Co‑related ADRs** | ADR‑009 (modular monolith) → single web container.<br>ADR‑010 (framework decision) → Python/Django 5, gunicorn, WSGI.<br>ADR‑036 (UI frontend) → HTMX/Tailwind assets built during image build; `collectstatic` in `dockerCommand`.<br>ADR‑005 (immutable journal) → migrations must run before any POSTED JEs; `dockerCommand` guarantees this.<br>ADR‑033 (tax feed) → env‑vars for any third‑party credentials stored as Render secrets (`sync: false`).<br>ADR‑035 (financial statements) → `collectstatic` must run before FS generation; included in `dockerCommand`. |
| **Implementation Outline** | 1. **`render.yaml`** (repo root) defines a Blueprint with:<br>   - Web service `stmiet-accounting`: `runtime: docker`, `rootDir: backend`, `dockerfilePath: ./Dockerfile`.<br>   - `dockerCommand`: `python manage.py migrate --run-sync && python manage.py collectstatic --noinput && gunicorn config.wsgi:application --bind 0.0.0.0:8000`.<br>   - PostgreSQL database `stmiet-accounting-db`, `postgresMajorVersion: '18'`, `databaseName: stmiet_accounting`.<br>
   - Env vars: `DATABASE_URL` ← `fromDatabase` (stmiet-accounting-db), `DJANGO_SETTINGS_MODULE=config.settings.prod`, `ALLOWED_HOSTS=.onrender.com`, `SECRET_KEY` ← `sync: false` (filled in Dashboard).<br>   - No Redis/Celery yet (deferred).<br>2. **Connect the GitHub repo** to Render → New Blueprint (Render reads `render.yaml` at the repo root).<br>3. **Fill in `SECRET_KEY`** in the Render Dashboard (only secret declared with `sync: false`).<br>4. **Deploy** – first deploy runs migrations + collectstatic; subsequent pushes incrementally apply new migrations.<br>5. **Monitor** – Render logs and health checks confirm the app is up.<br>6. **Future migration** – When scaling beyond Render's limits, export the Docker image and create K8s manifests (Deployment, Service, ConfigMap, Secret) – the app code does not change. |
| **Status** | Accepted |

*This ADR replaces any ad‑hoc deployment notes and becomes the single source of truth for how the STMIET Accounting System is released to production on Render.*
