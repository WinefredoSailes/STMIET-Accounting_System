# ADR-042 — Master Purchase Order (PO) Authorization for RFPs

| Field | Content |
|-------|---------|
| **Status** | Accepted |
| **Date** | 2026-09-15 |
| **Decision** | The AP module now has a first-class **Purchase Order** document (`PurchaseOrder` + `POLine`). Its layout mirrors the finance head's PO template (`PURCHASE ORDER_LIMDON.docx`), it is approved through the same head-trio + optional COO/CNR matrix as the RFP (ADR-020), and an approved PO can **authorize one or more RFPs** against the same vendor. Billing is a header-level **derivation from the linked RFPs** — never a stored counter — so the available balance is always exactly `amount − reserved (approved RFPs) − billed (posted RFPs)`. |
| **Context** | • ADR-017 scoped PO as future work ("no purchase-order screen"); RFP→CONSO→CV was the wired daily-cycle path.<br>• The finance head's master shows orders are PO-authorized: a disbursement should only be payable once its PO is approved, and a PO's remaining balance must bound the RFPs billed against it (partial billing).<br>• The PO template layout (PK: PO#/date/vendor, line grid PR-QTY-UNIT-DESCRIPTION-PRICE-AMOUNT, DISCOUNT/SUBTOTAL/VAT/OTHER/TOTAL, payment terms & contract duration, deliver-to block, AADB + CNR signature lines) is the source of truth for the screen.<br>• Grand total = subtotal − discount + VAT + other charges. Lines are qty × unit price. |
| **Decision Drivers** | 1. **One document per order, many disbursements** — a PO authorizes multiple RFP billings (partial billing), so the balance contract must live on the PO, not the RFP.<br>2. **Consistency with the RFP** — the same approval matrix, the same same-person guard, the same reject/revise cycle and audit log (`ActionLog` doc_type `po`).<br>3. **Derived not stored balances** — the free balance is recomputed from linked RFPs (`reserved`/`billed`/`available` properties). This eliminates counter-desync and makes the guard re-derivable under a PO row lock at the moment the RFP reaches its final approval.<br>4. **POs never post to the GL** — a PO is a commitment document; the RFP it authorizes carries the JE through CONSO (ADR-018). No duplicate postings, no extra posting-rule families. |
| **Consequences** | **Positive**<br>• RFP form gains a PO picker (`data-searchable`, `data-search-url=/ap/po-options/`) auto-scoped to the chosen vendor; only **approved** POs with remaining balance are offered.<br>• `RFPService._guard_po_balance()` re-checks the balance under `select_for_update` when the RFP enters `fin_approved`/`cnr_approved`, so two concurrent RFPs cannot over-commit one PO.<br>• Rejection/revise does not consume the PO balance; the RFP's reference survives the cycle (guarded again at create/revise).<br>• A posted RFP counts as `billed`; the RFP detail page links the PO chip and the PO detail shows AVAILABLE = amount − reserved − billed.<br>• Numbering is `{YYYY}-{SEQ:05d}` via the existing `DocumentSequence` pool (form code `PO`).<br><br>**Trade-offs / out of scope**<br>• PR and RR/Goods-Received are still not built (ADR-017). The PO screen records the source `PR No.` per line but does not enforce a PR exists.<br>• `closed` is an operational stop (head-only) that forbids further RFP references without voiding reservations already made by approved RFPs.<br>• PO-level line controls (reserved per line item) are intentionally **not** modeled — billing is header-level, matching how the team tracks balances. |
| **Revisit Trigger** | If the team begins reconciling line-item quantities (RR receipts vs PO lines), move billing to `POLine` (`reserved`/`reserved_amt` per line) and gate RFP lines on SKU-level availability instead of the header derivation. |
| **Co-related ADRs** | ADR-017 (purchase-to-pay chain) — this closes the PO row of its scope table.<br>ADR-020 (approval matrix) — PO reuses the head trio + COO/CNR matrix and same-person guard.<br>ADR-018 (RFP document model) — the RFP gains the `po` FK and balance guard; CONSO posting marks the amount billed.<br>ADR-008 (approval hierarchy) / ADR-006 (document-centric) — PO is a document with lifecycle + append-only audit. |
